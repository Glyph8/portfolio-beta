## 왜 이 글을 쓰는가

차콜 프로젝트는 2023년 12월부터 2024년 5월까지 3인 팀이 진행한 소셜 독서 기록 앱이었다. 출시 2주 전 팀이 해체되었고, 프로젝트는 미완성으로 끝났다. 성공 사례만 포트폴리오에 올리는 것이 당연하게 여겨지지만, 실패에서 배운 것이 훨씬 더 구체적이었기 때문에 이 회고를 남긴다.

---

## 무엇을 만들려 했는가

독서 기록을 소셜 피드로 공유하고, 같은 책을 읽은 사람들끼리 실시간 토론 채팅을 할 수 있는 서비스였다. 기술 스택은 다음과 같았다.

- **Frontend:** Next.js App Router + Zustand
- **Backend:** Spring Boot + WebSocket
- **Infra:** AWS EC2 + RDS (PostgreSQL)

---

## 무엇이 잘못되었는가

### 1. 기술 결정을 너무 이르게 확정했다

프로젝트 초기, 충분한 사용자 리서치 없이 "실시간 채팅"이 핵심 기능이라고 단정했다. WebSocket 인프라를 설계하고 E2EE 프로토타입까지 만들었지만, 실제 테스트 유저들은 채팅보다 **비동기 댓글** 형식을 더 선호했다. 6주간의 WebSocket 작업이 방향 전환과 함께 대부분 폐기되었다.

> 기술은 문제를 해결하는 수단이다. 문제가 확정되기 전에 수단을 먼저 정한 것이 첫 번째 실수였다.

### 2. 모노레포 전환이 오히려 속도를 늦췄다

3개월 차에 Turborepo 기반 모노레포로 전환했다. 공통 컴포넌트를 `packages/ui`로 분리하고, 백엔드·프론트엔드를 단일 저장소에서 관리하는 구조였다. 의도는 좋았지만 팀 규모(3명)와 프로젝트 단계(초기 MVP)에서는 명백한 과잉이었다.

빌드 캐시 무효화 이슈, 패키지 버전 충돌, Turborepo 학습 비용이 누적되어 2주간 실제 기능 개발이 거의 없었다.

### 3. 역할 분리 없이 시작했다

세 명 모두 "풀스택"을 지향했기 때문에 역할 경계가 불명확했다. 같은 API 엔드포인트를 두 사람이 동시에 작업하다 충돌이 발생한 적이 여러 번이었고, PR 리뷰 없이 main에 직접 push하는 관행이 자리 잡았다.

## 기술적으로 건진 것들

실패했지만 이 프로젝트에서 처음으로 아래를 직접 구현했다.

| 기술 | 배운 것 |
|---|---|
| WebSocket + STOMP | 연결 생명주기 관리, 하트비트, 재연결 로직 |
| PostgreSQL JSONB | 비정형 독서 메모 데이터를 유연하게 저장하는 방법 |
| GitHub Actions | 브랜치 전략 없이 CI를 운영할 때 발생하는 문제들 |

WebSocket 경험은 이후 TimeTogether 프로젝트에서 직접 활용되었다. 실패가 완전한 낭비는 아니었다.

## 다음에 다르게 할 것

1. **MVP 범위를 글로 먼저 정의한다.** 기술 선택 전에 "이 기능이 없으면 서비스가 성립하지 않는가?"를 팀 전체가 동의할 때까지 논의한다.
2. **팀 규모에 맞는 도구를 선택한다.** Turborepo는 10명 이상 팀에서 진가를 발휘한다. 3인 팀에서는 단순한 모놀리식 구조가 더 빠르다.
3. **PR 리뷰를 의식적으로 요구한다.** 귀찮더라도 리뷰 없는 merge는 기술 부채를 기하급수적으로 쌓는다.
